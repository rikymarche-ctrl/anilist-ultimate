# Friend activity alerts

Friend Alerts is an independent extension feature. It does not require Astra scoring or Notification Cleaner, and does not write simulated notifications into AniList's notification system.

## Using it

1. Sign in through the extension, then open an anime or manga page.
2. Choose the square bell to the left of the title's list status button. It sits outside the native actions row and preserves the status button's width.
3. Select **People I follow** or an existing custom friend list, such as **Best Friends**, and enable the alert.
4. Open AniList's **Notifications** page, then **Friend alerts**. **Activity** contains the updates; **Following** manages your titles and audiences. Compact toolbar actions check for updates or mark alerts read; the overflow menu clears the inbox. The title dialog also links directly to this inbox. There is no floating button.

The subscription covers public anime/manga list activity: progress and status changes published in the activity feed. Likes, replies, reviews, rating changes and private list edits are outside this first version. The activity link opens the original AniList activity. Changing a title's audience starts its subscription again from the current time.

## Collection and persistence

- One local inbox per authenticated extension account, shared across tabs on this browser. No remote inbox or browser/system push notifications are created.
- A background alarm schedules checks every five minutes while the browser/extension is running. AniList does not need to be open. After browser downtime, collection resumes from the saved checkpoint.
- Automatic and manual checks share a persisted five-minute minimum interval across tabs and worker restarts. Each wake makes at most **one HTTP activity request**. Titles with the same effective audience are grouped into an AniList `mediaId_in` filter; different audiences use aliases in that same GraphQL operation. There is **no six-title rotation**. Fifty titles with the same audience are checked together on every cycle; three matching activities return three rows rather than fifty separate title queries. User IDs/following, media IDs, time window and exclusion of the signed-in user are filtered by AniList.
- Each audience group requests one result page of up to 50 matching activities per cycle. More matching results continue from the saved page/window on the next scheduled cycle without extra immediate calls. Group membership is kept stable during a scan; a watchlist/audience change safely restarts the affected group from committed per-title checkpoints. Per-title start times prevent collecting activity older than a newer subscription. Existing per-title scans migrate from their committed checkpoint, retaining the inbox and fingerprints.
- Requests use the shared query-size/selection budgets rather than an arbitrary title count. AniList's documented 10,000-ID filter maximum splits exceptionally large title groups. If many very large audiences exceed the shared request budget, groups checked least recently take priority in subsequent cycles; the host still sends at most one request per five-minute interval. Empty/deleted/self-only audiences do not issue a request.
- Scheduled checks use the common API queue and rate limiter with automatic retries disabled: a failed request waits for the next five-minute cycle. Opening the inbox, reading alerts or changing tabs/pages does not query AniList. The foreground's periodic inbox refresh reads local storage only. Enabling a new title performs a separate metadata lookup. Changing an existing title's audience reuses saved metadata; saving an unchanged subscription makes no API request and does not reset its start time.
- Watched titles have no fixed count limit. The latest 200 alerts are stored. Both inbox views paginate 25 rows at a time without restricting the number of subscriptions. Initial subscription excludes older activity. An unfinished scan saves its time window and next page for the next wake.
- Activity IDs and status/progress fingerprints prevent duplicate alerts. The last 50 fingerprints per title survive clearing the inbox. To detect merged progress with an unchanged creation time, the same request also looks up up to 50 known activity IDs **per audience group**. When there are more known IDs, these lookups rotate; the fresh activity filter still includes every title in that group. The provider skips the lookup entirely when there are no known IDs. An unchanged replay does not mark an existing read notification unread. There is no independent history of edits that AniList does not publish as activity.
- Polling requests only ID, media ID/type, actor ID/name, status, progress and creation time. Saved subscription titles supply the inbox labels; avatar/cover images, title translations, reply counts and like counts are not requested for alerts.
- Custom list membership is read on each check. Empty/deleted lists never become unfiltered activity queries. Users do not have to be followed to belong to a custom audience.
- **Modules → Social Features → Friend Alerts** is an independent switch. Turning it off stops new background checks and removes the bell/inbox from already-open AniList tabs without reloading. Turning it back on restores saved subscriptions and alerts. Disabling Astra has no effect on collection. A lightweight settings listener remains available to reactivate the UI; disabled views have no refresh timers or DOM observers.
- Failed provider calls keep their checkpoint for retry and display a partial-failure message. Failed storage writes propagate; malformed stored data is preserved rather than reset.
